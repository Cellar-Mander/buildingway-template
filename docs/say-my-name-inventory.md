# say-my-name setup: generic vs project-specific

Spike 68959a5b, 2026-11-05. Source: `~/Repo/say-my-name` at `fcb4e8b` (v1.0.0.1), its 272-commit
history, and the GitHub repo's settings. Feeds the template tool decision and template v1's contents.

Legend:
- **Generic**: copy as is; only the plugin name changes (parameter `{Name}`, `{name-kebab}`, `{Author}`).
- **Parameterised**: the shape is generic but it has project values worth templating.
- **Specific**: say-my-name's own; leave out of the template (or ship only a stub).

### release.yml lessons (each one a fix after something went wrong)

1. Main only takes PRs, so repo.json goes via a force-pushed `release/repo-json` branch and PR (63932a1).
2. PRs and pushes made with `github.token` start no workflows, so required checks never report; the release dispatches `test`, `workflow-lint` and `pr-build` on the branch (dd6c89c, 48b7a33, 8c5bebe). **Every required check's workflow must accept `workflow_dispatch` and be in that list.**
3. A tag pushed with `github.token` starts no workflow, so one run tags, builds and publishes (d32261f, 4d58df8).
4. Dalamud only updates to a higher version, so each testing build needs its own `<Version>`; a second RC at the same version is refused (a49078f).
5. Testing channel sets only `Testing*` fields; a stable release rebuilds the entry and so ends testing (4d58df8).
6. Tag must match the manifest's `AssemblyVersion`, checked before publishing.
7. Stable refuses while `## Unreleased` has entries (they'd be missing from the notes).
8. `concurrency: release` so two runs can't race on repo.json.

## GitHub repo settings (not in files; a template can't carry them)

| Setting | Value | Note |
|---|---|---|
| Ruleset "Protect Main" | PRs only, no deletion, no force push; required checks `test`, `build`, strict | **Gap:** `actionlint`/`zizmor` are not required, though 48b7a33 was done so they could be |

| Merge methods | all three on; no auto-delete branches | Not a deliberate choice as far as history shows |

These need a setup step (script using `gh api`) or a checklist; a file template alone won't apply them.

## What dropped out (don't re-add)

- CodeQL trial: without a build it resolved none of Dalamud's namespaces and has no model of chat as untrusted input, so 0 alerts meant nothing (820672d → 0a72b5f).
- Auto-tag on `<Version>` change with approval environment, replaced by dispatch with a channel (d32261f → 4d58df8).
- Config migrations before the first release (77dff16).

## Sizing for the template decision

- Name substitution is the main parameter: `SayMyName` (PascalCase, project/namespace/paths), `say-my-name` (repo), `Say My Name` (display), `/saymyname` (command), `SAYMYNAME_DEV_DIR`. 110 occurrences (grep, case-insensitive) in tracked files outside plugin `.cs`, README, CHANGELOG, docs and repo.json.
- Beyond the name, per-project values are few: author, repo URL, Dalamud pin, punchline/description/tags.
- Roughly 25 of ~40 non-code files are generic or need only the name; the rest are stubs or project content.
- State that changes after generation (Dalamud pin, vendored tool versions, workflow fixes like the ones above) argues for a template that can be re-applied or diffed against, not a one-shot copy: say-my-name gained 8 release fixes in 9 days after scaffolding.
